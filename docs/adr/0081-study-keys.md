# 81. S starts studying; 3 and 4 pass

- Status: Accepted
- Date: 2026-11-09
- Refers to: Phase 3b brief, slice 6; ADR 0037 (keys of the review page), 0064 (key hints in tooltips), 0065 (the deck page's keys)

## Context

Studying is the main thing Rappel does, but starting a session needed the mouse or Tab to the Study button, and Anki users reach for 3 and 4 (Good, Easy) as well as 2.

## Decision

- **S is decided by a pure function.** `ui::keys::starts_studying(key, modifiers, text_focus)` is true only for a plain S (or Caps Lock's S) with no text field focused. Ctrl, Alt, Shift, Super, Meta and Hyper make it another shortcut (Shift+S is Suspend in review) and give false.
- **S acts on its release.** A held key repeats as further key presses with no release between (`key-pressed` and `key-released` of `GtkEventControllerKey`, gtkeventcontrollerkey.c). Starting on the press put the session on screen under the repeats, and the session's own S (Suspend) suspended cards one after another (found in review: six cards in 2.5 s). So `ui::keys::StartHold` swallows the press and every repeat on the page that stays, and the first release starts the session once, if no text field has the focus by then.
- **A hold is only the last key press, on the same target.** `StartHold<T>` records the result of *every* key press the page sees (`held = target` when it is S, `None` for any other key), so Ctrl, Shift, Return or any other press cancels a held S. The release must itself be a plain S (no Ctrl, Alt, Shift or Super in its modifiers). `T` is what S would start, taken at the press and compared at the release: `()` on a deck's page (`None` while cards are being chosen), the deck's id on the deck list, so S pressed on one row and released on another starts nothing. A second key controller in the capture phase sees every press before any child can claim it (Return on a row or on a menu button never reaches the page's bubble phase) and cancels the hold for anything but a plain S. The page also forgets the hold when it starts hiding, is unmapped, or the focus leaves it (`ui::keys::when_left`: `AdwNavigationPage::hiding`, `GtkWidget::unmap`, `GtkEventControllerFocus::leave`). Found in review: S held on a row, Return opened the deck (the row's own binding takes Return, so the list never saw that press), S went up on the deck page; back on the list, Ctrl+S started a session from the stale hold.
- **In a session, S suspends one card per press.** The settle time (a card must be on screen 300 ms, ADR 0037) alone let a held S suspend a card every 300 ms. `ui::keys::OnePress` lets only a press that follows the release of the key that last acted (the first press on the page too); the key is matched by its hardware keycode, recorded by a capture-phase controller before the Suspend shortcut acts, because with a non-Latin layout the key marked S gives another value (`Cyrillic_yeru`) that GTK's shortcut matching still takes for S (`gdk_key_event_matches`, gdkevents.c, gives a partial match when the keycode gives S in another layout), so a check of the release's value would never re-arm; every press counts, one too early included, so a held S never suspends a second card. The release is seen by a second `GtkEventControllerKey` in the capture phase with no `key-pressed` handler: it claims no release (gtkeventcontrollerkey.c returns TRUE for a release only when it handled the press), and shortcut triggers match presses only (gtkshortcuttrigger.c). A release that went elsewhere (the editor, another page) is covered by `when_left`, which re-arms S. Undo toasts are unchanged: one press, one card, one toast.
- **Deck page:** S activates `deck.study`, so it does nothing when the Study button is disabled (nothing to study) and while cards are being chosen. **Deck list:** S on a focused deck row (the row, or its menu button) pushes (on the release) a session for that deck, started from the deck list ("Back to Decks"), without pushing the deck page first; a deck with nothing to study does nothing, as its page's disabled button would.
- **Review page and practice:** 3 and 4 are added to the page's key table beside 2, so they pass exactly as 2 does: the same settle delay against key repeat, no effect before the answer is shown, and in a practice nothing is rescheduled. The grades are not decided by the pure function: the page binds them as GTK shortcut triggers (so an AZERTY keyboard, where digits need Shift, behaves as GTK maps it), in the bubble phase, where a focused text field has already taken the key; a test checks the table.
- **Shown:** the Study buttons' tooltip is "Study (S)" (the translatable `{name} ({key})` of ADR 0064). The Keyboard Shortcuts dialog gets Start Studying (S) and Pass lists 2, 3, 4 and Space; its test checks both by name, since S is also Suspend in review.

## Consequences

Starting studying with S is decided by the key's value (`s`/`S`), as `starts_studying` is a pure function of it: under a non-Latin layout the key marked S does not start a session on the deck pages, while the review page's Suspend, a GTK shortcut trigger, still matches it. Making the deck pages match by keycode too (`gdk::KeyEvent::matches` against the event) would need the event in the pure function; it is left as a known limit.

Whether there is anything to study is decided once, by `StudyInput::is_empty` in `rappel-core`: the deck page enables `deck.study` with it, and the deck list's S checks it before pushing a session. The two callers differ only in what else they do with the input (the deck page also shows the counts), so there is no further shared function to factor out.

3 and 4 do not grade differently: FSRS here has two grades. The accessible descriptions of the grade buttons still say "Press 2 or Space"; they stay true.
