# 89. Bundled symbolic icons under app-specific names

- Status: Accepted
- Date: 2026-11-18
- Refers to: ADR 0086 (icon names in the snap; its amendment has the cause), ADR 0085 (the snap); the 0.4.2 request "icons missing in the snap"

## Context

In the snap some symbolic icons draw as "image missing". ADR 0086's amendment found why: GTK takes the icon theme's name from the desktop, the snap cannot see a theme installed in the user's home (here `Haru`, in `~/.local/share/icons`), and GTK 4.24 then searches `hicolor` alone, without Adwaita. Only the icons GTK and libadwaita bundle in their own resources survive that; 9 of the 30 names Rappel used did not. The same happens to any theme name the snap cannot see, and nothing in `snap/snapcraft.yaml` can make a folder in the host's home visible under strict confinement. A theme can also simply lack a name, or draw it differently, outside the snap.

## Decision

- Every symbolic icon Rappel's own sources name is bundled in the app's `GResource` and named with the app id as prefix: `io.github.rappelapp.Rappel-<Adwaita name>` (for example `io.github.rappelapp.Rappel-edit-undo-symbolic`). The Blueprint files and the Rust code use only those names.
- The files are in `crates/app/data/icons/scalable/actions/`, listed in `data/resources.gresource.xml` as `icons/scalable/actions/<name>.svg` under the prefix `/io/github/rappelapp/Rappel`. `GtkApplication` adds `<resource base path>/icons` to the default icon theme by itself, and GTK treats such resources as part of `hicolor` ("The resources are considered as part of the hicolor icon theme and must be located in subdirectories that are defined in the hicolor icon theme, such as `@path/scalable/actions/run.svg`", `gtk_icon_theme_set_resource_path`, `Gtk-4.0.gir`; "GtkApplication will also automatically setup an icon search path for the default icon theme by appending "icons" to the resource base path", `GtkApplication`, Automatic resources). `hicolor` ends every theme chain, so the icons are found whatever the theme, and no theme has an icon of that name to replace them.
- The 30 icons, and the right-to-left variants Adwaita has for four of them (`edit-clear`, `edit-undo`, `go-next`, `go-previous`, as `…-symbolic-rtl.svg`, which GTK picks in a right-to-left locale), are copied unchanged from adwaita-icon-theme 51.0 (`/usr/share/icons/Adwaita/symbolic/*/`, the Ubuntu package): plain paths with one `fill` colour, which GTK replaces with the foreground (and the `.error`, `.warning`, `.success` colours) for any file named `…-symbolic.svg`, as it does for the theme's own copy. No colour is hard-coded beyond that.
- Licence: adwaita-icon-theme states for these files (its `Files: *`; none of them is under a file-specific stanza of the package's `copyright`) "either the GNU LGPL v3 or Creative Commons Attribution-Share Alike 3.0 United States License", attribution "GNOME Project". Its copyright file gives the whole field as "CC-BY-SA-3.0 or LGPL-3, and CC-BY-SA-4.0"; the 4.0 term is for the sources it ships beside the icons (`src/symbolic/gnome-stencils.svg`), and CC BY-SA 4.0 is one-way compatible with GPLv3 anyway. The About dialog credits them in a legal section of its own ("Adwaita Icons", © GNOME Project, `GTK_LICENSE_LGPL_3_0_ONLY`, as the notice names no later version). Rappel uses them under the LGPL v3, which is compatible with its GPL-3.0-or-later. `crates/app/data/icons/NOTICE` gives the source, the authors and that statement, and `crates/app/data/icons/LGPL-3.0.txt` the licence text (the GPL v3 it adds to is the repository's `LICENSE`).
- The guard `crates/app/src/icon_names.rs` (tests only) now requires every `*-symbolic` name in `data/*.blp` and `src/**/*.rs` to be bundled; ADR 0086's allow-list of the names `gnome-core26` ships (`data/gnome-core26-icons.txt`) is removed. It also checks that every bundled icon has the prefix, ends in `-symbolic` (or `-symbolic-rtl`) and is used; that the folder and the manifest list the same files; that the SVGs load nothing else (no script, image, style, link or class); and, with GTK, that a theme with a name that does not exist and no theme folders, the snap's case, finds every name used, finds no unbundled name with the prefix, and takes the `-rtl` file for a right-to-left lookup.
- `snap/snapcraft.yaml` is not changed: no setting there makes a theme in the host's home visible, and with every icon bundled the theme the snap sees no longer matters for Rappel's own icons.
- To add an icon: copy the symbolic SVG from adwaita-icon-theme (or draw one with plain `fill` paths) to `crates/app/data/icons/scalable/actions/io.github.rappelapp.Rappel-<name>.svg`, with its `-rtl` variant if Adwaita has one, list it in `resources.gresource.xml`, and use the prefixed name. A file from elsewhere needs its licence added to `NOTICE`.

## Consequences

- Rappel's own icons look the same in every theme: Adwaita's drawing, recoloured as usual. A theme such as Yaru no longer restyles them (the host's Yaru drew them before, natively). Icons that GTK and libadwaita widgets name themselves (a dialog's close button, a search entry's clear icon, the window controls) still come from the theme or from GTK's and libadwaita's own resources; they are not Rappel's names.
- About 34 small SVGs (some 20 KB) more in the binary.
- Icons outside the app's own sources are not guarded: a name built at run time would not be found by the scan (the app builds none).
