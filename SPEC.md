# Rappel — SPEC

A native GNOME flashcard app. Rust, GTK4, libadwaita, Blueprint. Two grades only: **Fail** and **Pass**. Cards are Markdown with LaTeX math. Scheduling is FSRS. Everything is local: no network access, no accounts.

App name: **Rappel**. App ID: `io.github.rappelapp.Rappel`. Licence: **GPL-3.0-or-later**.

- Crates: `rappel-core` (`crates/core`, library) and `rappel` (`crates/app`, GTK binary).
- Data directory: `~/.local/share/rappel/`. Debug builds use `~/.local/share/rappel-dev/` so development never touches real data. Both can be overridden with the `RAPPEL_DATA_DIR` environment variable.

v0 is released as 0.1.0: decks, plain-text cards, review with Fail/Pass, FSRS, SQLite. Phase 1 of the roadmap (§4), text only, reached its beta, 0.2.0-beta.1. Phase 2, media and mobile, is done and reached its beta, 0.3.0-beta.1 (tagged). Neither 0.2.0 nor 0.3.0 is released as stable: each phase went on from the previous beta. **Phase 3a**, organising and studying (§4), is done and reached its beta, 0.4.0-beta.1 (tagged) (done: the small polish, ADR 0064, selection mode on the deck page, ADR 0065, merging decks, ADR 0066, archiving decks, ADR 0068, studying by tag, ADR 0069, practice mode, ADR 0070, and phase 2's leftovers, ADR 0071, and the editor's note on a front another card has, ADR 0072, and the fourth clean-up and hardening round, ADR 0073); 0.4.0 closes phase 3b; **Phase 3b**, polish and the first Snap (§5), is done except the Snap, which stopped at the image sandbox (ADR 0082, `docs/briefs/QUESTIONS.md`); 0.4.0 is released (tagged) without a Snap; the Snap resumed in `docs/briefs/phase-3b-snap.md` (the image loader runs without bubblewrap in Rappel's own snap, ADR 0055 amendment; packaged with `snap/snapcraft.yaml`, `scripts/snap-install.sh` and a CI build that never publishes, ADR 0085), for 0.4.1 on the Snap Store's beta channel (tagged; 0.4.2, French wording and an icon-name test, is prepared, not tagged; report `docs/briefs/phase-3b-snap-report.md`); **Phase 3c**, the Flatpak bundle, a translation workflow for volunteers and hardening, ends in 1.0 (§5). ## Product vision

Rappel is an opinionated, modern GNOME flashcard app. It is closer to Mochi than to Anki.

- **Efficiency is not maximalism.** Studying well takes few cards, few buttons and few decisions. Rappel does not try to cover every way anyone has ever used flashcards.
- **Smart behaviour is built in and invisible until needed** (progressive disclosure). The scheduler, the daily limits, the backups and the search just work. A feature shows itself when the user reaches for it, not before.
- **Every setting must justify itself.** If a good default can be found, there is no setting. A setting that needs a paragraph to explain is a design failure.
- **Anki is a source to import from, not a model.** Rappel has no note types, no add-ons, no field templates and no per-deck presets, and will not grow them. An Anki collection comes in as plain cards.
- **Card links belong to the separate method app**, not to Rappel (see §6).

## 1. Principles

1. **Data first.** Losing review history is the worst possible bug. Backups, export and migrations come before features.
2. **Core is UI-agnostic.** `rappel-core` holds all logic and has no GTK dependency. It must stay testable with plain `cargo test`.
3. **GNOME-native.** Follow the GNOME HIG. Use libadwaita widgets as designed. No custom colors, no web views.
4. **Few options, good defaults.** A setting needs a reason to exist (see the product vision).
5. **Untrusted content.** Card text may later come from imports. It is never interpreted as HTML or markup without escaping. Card content never causes network access or access to user files. Reading installed system fonts is allowed (ADR 0021).
6. **Adaptive from phone (360 px) to desktop, touch-friendly, ready for mobile Linux.**

## 3. Data model changes

Keep everything from v0 (migration 0001, ADR 0005). Ids are UUIDv7 stored as `TEXT`. Timestamps are UTC milliseconds. `cards` also has an internal `seq INTEGER PRIMARY KEY`, a stable integer key for FTS5 that is never exported. `review_events` is the source of truth; `card_schedule` is a cache rebuilt from it. Triggers forbid `UPDATE`/`DELETE` on `review_events`, and a card with reviews cannot be deleted (`ON DELETE RESTRICT`), so card deletion is a soft delete. Add, via numbered migrations:

```sql
ALTER TABLE cards ADD COLUMN suspended INTEGER NOT NULL DEFAULT 0;  -- excluded from study and from the schedule's statistics (ADR 0035)
ALTER TABLE decks ADD COLUMN archived_at INTEGER;  -- migration 0012: NULL, or when the deck was archived (UTC ms); an archived
-- deck is live (its name stays taken) but out of the deck list, study and the global forecast and retention (ADR 0068)

tags(id TEXT PRIMARY KEY, name TEXT NOT NULL, name_key TEXT NOT NULL UNIQUE);
-- Flat, unique by name key (trimmed, NFC, lower-cased, as decks), never deleted (ADR 0029).
card_tags(card_id TEXT REFERENCES cards(id) ON DELETE CASCADE,
          tag_id  TEXT REFERENCES tags(id)  ON DELETE CASCADE,
          PRIMARY KEY(card_id, tag_id));

-- Undo and reset without breaking the append-only log (ADR 0028):
review_events.kind   TEXT NOT NULL  -- 'review', 'reset' or 'undo'; grade only on a review
review_events.undoes TEXT REFERENCES review_events(id)  -- only on an undo, unique
-- A reset makes the card new from there on. An undo cancels the card's latest
-- review or reset that is not already undone. rebuild_state skips undos and
-- the entries they cancel, and starts again at a surviving reset.

settings(key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- desired_retention (0.80–0.97, default 0.90), max_new_per_day (0–9999, default 20),
-- max_reviews_per_day (0–9999, default 200), day_start_hour (0–23, default 4).
-- A key never written has its default. Limits are per deck (ADR 0027).
-- A stored value outside its range stops the open, naming the key; the app offers
-- "Reset This Setting", which backs up and then removes that row (ADR 0052).

media(hash TEXT PRIMARY KEY, mime TEXT NOT NULL, bytes INTEGER NOT NULL, created_at INTEGER NOT NULL);
-- One row per file of <data dir>/media/<hash>.<ext> (ADR 0054): the SHA-256 as 64 lowercase
-- hex digits, one of the MIME types of the kinds kept (image/png, image/jpeg, image/webp,
-- image/gif, audio/ogg, audio/mpeg, audio/mp4, audio/wav), bytes > 0, checked by the schema.

-- Full-text search (ADR 0035): a cache of the plain text of each side (what the user
-- reads, folded to lower case without accents), written by the store with every card write.
CREATE VIRTUAL TABLE cards_fts USING fts5(front, back, tokenize = 'unicode61 remove_diacritics 0');  -- rowid = cards.seq
```

Storage rules:
- `PRAGMA journal_mode=WAL`, `foreign_keys=ON`, `PRAGMA integrity_check` at startup (log and toast if it fails).
- **Backups:** before any migration, and once per day at startup, copy the DB with the SQLite online backup API to `<data dir>/backups/rappel-YYYYMMDD-HHMMSS.sqlite3`. Keep a backup if it is from the last 24 hours, or the newest of its UTC day for each of the last 14 days, or the newest one overall, or the one just made or just restored (ADR 0026); a backup dated in the future (a clock that ran ahead) is kept if it is the newest of its UTC day, for the 14 latest such days, and finishing an interrupted restore prunes nothing (ADR 0050).
- DB and backup files are created with mode `0600`, directories `0700`.
- A restore never replaces a copy an interrupted restore left waiting: it is kept as `rappel.sqlite3.restore.set-aside-YYYYMMDD-HHMMSS` (ADR 0052). Nothing in the data folder is ever deleted by a restore.
- **Media trash** (ADR 0057): a media file no card names (live or deleted) can be moved by Clean Up Media to `<data dir>/media-trash/<YYYY-MM-DD>[-N]/<sha256>.<ext>` (the UTC date; a name in the trash is never reused), its row deleted, in one write transaction that puts everything back on failure. A trashed file the database uses again (a row after a crash or a restore, a card side after an import, a restore or a card write) goes back to `media/`, with a row made from its name and size if needed. A dated folder's files are deleted once the clock is 31 days past its date and the database records a user action (review, card or deck change) 30 days past it (a folder is dated by the latest of today and the times the data and the trash hold, so never earlier than the clean-up), unless a backup, the waiting restore copy, another copy of the database in the data folder or the database uses them; a backup that cannot be read keeps everything. That is the only deletion of a user's file. Adding a media file names it and commits its row under the write lock.

### 4.1 Export / import
- Export everything to one `.rappel` file (older `.cards` files import too, ADR 0020): a zip archive holding exactly `cards.json`, a `media/` folder and one entry `media/<sha256>.<ext>` per media file, stored as it is (ADR 0017, 0054). `cards.json` has `"format_version": 2`, `exported_at`, and all decks, cards, tags, card tags and the full review log with its resets and undos, deleted rows included with their `deleted_at`. Each card record has `suspended` (always written; a file without it reads as `false`, ADR 0035). Each deck record has `archived_at` after `updated_at` (always written, `null` when the deck is not archived; a file without it reads as not archived; any value but `null` or a timestamp in range is refused as that field: a string, a fraction, a boolean, an array or an object as "not a timestamp", a negative or too large number as "timestamp out of range"; ADR 0068). It also has `settings` (the keys the user changed, ADR 0027) and `media`: one record per media file (`hash`, `mime`, `bytes`, `created_at`, sorted by hash), whose file is `media/<hash>.<ext>` (ADR 0054). A media file missing or damaged at export is left out with its record, and the export says how many.
- Versions: version 1 was written only by test versions (0.2.0-alpha, and `.cards` files) and is refused with "made by an early test version of Rappel and cannot be imported" (ADR 0017). **From 1.0 on, every format version a release wrote stays importable by every later release.**
- Deterministic: the same database exported at the same time gives the same bytes (lists sorted by id, fixed zip metadata). Only `exported_at` differs between exports.
- Import into an empty or existing DB in two steps: `plan_import` checks the file and returns a summary without writing anything (new / already present / conflicts, e.g. "12 decks, 840 cards, 5,210 reviews"); `apply_import` backs up the database, then writes in one transaction and rebuilds the schedule of the affected cards from the log.
- Merge rules: an id not in the DB is added; the same id with the same content is skipped. A media file whose hash the DB has with the same type and size is present (the DB keeps its own `created_at`), with another type or size a conflict; a new one is copied into the media folder before the transaction commits. A card may name a media file that is in neither the file nor the DB. A tag whose name key a DB tag with another id has is mapped onto that tag (its card tags attach to the DB's id), not added; a tag with the same id and another name is a conflict, and so is an undo of an entry the DB has already undone. The file's settings are applied only into a DB without decks (deleted ones included); otherwise the DB keeps its own. A card that differs only in `suspended` is already present: the database keeps its own flag, since an import never changes how a live card is studied (ADR 0035). Likewise a deck that differs only in `archived_at` is already present and keeps the database's flag (a deck the import revives keeps it too), and a new deck keeps the file's; the Anki import never archives a deck (ADR 0068). Likewise a card that differs only in its deck is already present and keeps the database's deck: an import never reorganises cards, so an export made before a Move to Deck or a merge imports again; the file's deck is added or revived by its own row, without the card (ADR 0067). The summary counts the cards that stay live in another deck than the file's, and the import dialog says it ("3 cards are in another deck in the file and stay in the ones they are in now."). So cards moved on one machine keep the other machine's deck when its export is imported there (a new deck "Verbs" made for them arrives empty), and after a merge an older backup brings the merged deck back empty. A row that differs only by being deleted is merged: deleted in the DB and live in the file, it is revived (`deleted_at` cleared; a revived deck also revives the cards deleted with it, as `undelete_deck` does, except those the file has, which follow their own row); live in the DB and deleted in the file, it is skipped (an import never deletes); a card revived this way stays in its own deck, and stays deleted if that deck is deleted and not revived by the import (ADR 0067); deleted on both sides, at whatever times, it is already present. The same id with any other difference, or a live deck name (revived ones included) already used by another live deck, is a conflict, and any conflict refuses the whole import. The summary also counts revived rows. Importing the same file twice changes nothing.
- The file is untrusted. A file is refused if any of these fail: size limits; the exact entry names (nothing is extracted, so no zip-slip); each media record with exactly one entry of its size and each media entry with a record, whose content has the record's hash and type (read before anything is written); a supported format version; every id a lowercase `UUIDv7`; references that resolve; valid kinds, grades and timestamps; undos that cancel an earlier review or reset of the same card, once; tag names without a NUL or a comma; settings within their ranges; no NUL character in a deck name or card side.
- Round-trip test: export → import into empty DB → export again produces an identical file.
- The automatic backup (§4.8, ADR 0080) writes this same export into a folder the user chose, once a day at close.
- *Done (ADR 0071):* an export that an import would refuse for its media is announced before anything is written. Export… adds up the `media` table's sizes with their entries' headers (a lower bound of the file: `cards.json` counts as empty, so the question is never asked of an export that would import) and asks "Export Without Media?" when that is past the 2 GiB an import reads (`MAX_ARCHIVE_BYTES`, shared with the import's limit) or when the entries would be past the 100,000 it reads. The body says which, in words true of the case: "With its media files, the export would take at least {size} (rounded down), more than the 2 GiB that Rappel reads from one file, so Rappel could not import it again.", or "The export would hold {count} media files, too many files for Rappel to read from one export, …", each followed by "Export without the media instead? Decks, cards and their history are exported; the media files stay where they are, and cards keep their references to them." Responses Cancel (the default and the close response, so Enter never exports) and Export Without Media, which writes the normal format version 2 with an empty `media` list and no `media/<sha256>.<ext>` entry (no format change; cards keep their `media:` references, which an import allows). The success toast stays and says media were left out. The file is checked after writing: one over the limit (the text of `cards.json` pushed it over) is not kept, and the same question is asked, "The export came to {size}, more than the 2 GiB that Rappel reads from one file, so Rappel could not import it again. It was not saved. …"; on yes it is written again to the same path without media. If even that is over the limit, or there were no media to leave out, the error toast says "The export failed: even without its media it came to {size}, …". Not checked beforehand: a `cards.json` over 256 MiB, which leaving the media out does not mend. Tested: without media it imports into an empty database, round-trips and is deterministic; the decision is a pure function exact at the boundary, and never more than a real export.
- *Done (ADR 0071):* a file is refused early from what it declares: the file's size, the entry count and the central directory's size from the end record, and `cards.json`'s and each media entry's declared sizes from the central directory, before any of them is read (the checks while reading stay, since declared sizes can lie). Checking a file shows a toast, "Checking the file…", with Cancel (and Escape) that stops the reading within moments and writes nothing ("Import cancelled"); the Anki import has the same.
- **Streaming import** (phase 2, first; *done*, ADR 0053): `plan_import` and `apply_import` read the archive entry by entry and keep memory bounded (under 200 MiB at the limits: an archive of 2 GiB with at most 100,000 entries, 256 MiB of `cards.json`; an image at most 10 MB, an audio file 20 MB), so a file with a large media folder does not need to fit in memory. The plan keeps compact notes and a fingerprint of the file; the apply reads the file again, refuses it if it changed, and writes in one transaction. The checks and merge rules above do not change, and a refused file still writes nothing, so media are not put in the store before the plan is confirmed.

### 4.2 Math
- `$...$` inline and `$$...$$` display math in Markdown.
- Rendering: evaluate **RaTeX** first (pure-Rust, KaTeX-compatible, has `ratex-cairo` and a `ratex-gtk4` widget). Draw inline math as vectors in the text flow, on the text baseline; display math as a centered block (ADR 0021). Formula color follows the theme foreground (works in dark mode).
- Fallback if RaTeX doesn't work out: show the LaTeX source in monospace. Never a web view.
- Invalid LaTeX shows the source with an error style, never crashes.
- Record the decision in `docs/adr/`.

### 4.3 Images
- Paste or drag an image into the card editor. It is copied into the media store (`<data dir>/media/<sha256>.<ext>`, folder `0700`, files `0600`, a file never replaced by another) and referenced as `![](media:<sha256>.<ext>)`. Its type comes from its first bytes, never its name (ADR 0054).
- Only `media:` URLs render. Remote URLs and arbitrary file paths are shown as text, never fetched.
- Accept PNG, JPEG, WebP, GIF (shown still); **no SVG** (script/external-reference risk). Max 10 MB. Audio: Ogg (Opus or Vorbis), MP3, M4A, WAV, max 20 MB (ADR 0054).
- *Done (ADR 0055):* decoded by glycin in its loader process, off the main thread: under bubblewrap with seccomp and a memory limit where the system allows (flatpak-spawn in a Flatpak), else, where no namespaces can be made, as a plain separate process (logged as a warning); in Rappel's own snap only (`$SNAP` set, `$SNAP_NAME` `rappel`, the binary inside `$SNAP`), as a plain separate process by choice, bounded by the snap's strict confinement, said once at start-up (ADR 0055 amendment, ADR 0082 amendment); only the media folder's regular files, of their kind by their first bytes (which is what keeps SVG out), within 16,384 px a side and 64 MP, a 10 s timeout and the decoder's own type matching the file's kind; scaled down to the card's width and 60 % of the view's height (never up), at most 20 per side, opened at full size by a click or Enter / Space; the alt text is the accessible name; a missing or bad file is a placeholder. In the editor: an Insert Image… button per side, Ctrl+V of image files or a picture, and dropping files or a picture on a side (only local files are read, never a URL; a picture is taken as the bytes offered, never decoded in Rappel's process), inserted at the cursor (or the drop point) as one undoable step with the cursor in the alt text.

### 4.9 Audio

### 4.11 Anki import
- **Anki `.apkg` import**, one way. Cards, tags and review history become plain Rappel cards; note types, templates, add-ons and presets are dropped, not mapped (product vision). Field HTML becomes Markdown or plain text and is never rendered as HTML; Anki's four buttons map to two grades (Again = Fail, the others = Pass); cloze notes come in as ordinary cards with the text shown in full; `<img>` and `[sound:]` become `media:` files (no SVG, remote URLs stay text). An `.apkg` is an untrusted archive holding an untrusted SQLite database, so it gets its own limits and checks in the slice's ADR, as §4.1 has for `.rappel`.
- *Done (ADR 0061):* Import… takes Anki packages (`.apkg`, and `.colpkg`, the whole collection), in Anki 2.0's, 2.1's and the current format (zstd, schema 18), told from a `.rappel` file by name or content. Each Anki card is one card (both directions of reversed notes; a cloze card shows its cloze as `[…]` or `[hint]` on the front and in bold on the back), rendered with its template (fields, sections, special fields and the common filters; an unknown filter shows the field and is reported) and converted to escaped Markdown (`\(…\)` → `$…$`, `\[…\]` → `$$…$$` when Rappel can draw it; links for web and mail only; `<script>` and `<style>` dropped). Decks `A::B` become `A › B` (cards of filtered decks go home, a deck with a live deck's name is merged into it); tags are kept; images and sounds the package has, of the kinds Rappel keeps, become media files (no SVG, remote images stay text); suspended cards stay suspended; the log keeps learning, review and relearning entries (Again = Fail, the others = Pass) and the schedule is rebuilt from it (manual and cram entries left out, a forgotten card reset). A card identical to a live card (deck, front, back) is not added again, so importing twice adds nothing. The plan lists what is left out or changed, with counts and examples; the import backs up, writes in one transaction, and can be cancelled. Limits: those of §4.1's archive, 2 GiB of collection, zstd windows of 32 MiB, the collection read-only and defensive (no triggers, no views).

## 5. Phase 3b, phase 3c and later

**Phase 3b — polish and the first Snap, ends in v0.4.0** (brief `docs/briefs/phase-3b.md`): everything found since 0.4.0-beta.1 is polished and fixed, the app ID moves to `io.github.rappelapp.Rappel` (the repository is now rappelapp/rappel; the data directory does not change), and the first Snap was to be built and published on the Snap Store. The Snap then resumed (`docs/briefs/phase-3b-snap.md`): images in the snap (ADR 0055, amendment) and the packaging (ADR 0085: strict confinement, the desktop plugs and `audio-playback`, M4A not supported in the snap), for 0.4.1. The brief lists the slices and what is pre-approved.

**Phase 3c — Flatpak and volunteers, ends in v1.0**, in this order (translation, once planned here, moved to phase 2: §4.12; the features of phase 3a are in §4):
1. **Testing campaign**: testers use the app on real collections, on desktop and phone, before 1.0; what they find is fixed before release.
2. **Publishing, the rest**: a self-hosted Flatpak bundle (with its manifest, written by hand) next to the Snap, installing the `.mo` files and setting `RAPPEL_LOCALEDIR` (ADR 0059); the finished AppStream metainfo and `.desktop` entry, drafted in `data/` (ADR 0060), with their translations merged (`build.rs` already merges them and `scripts/snap-install.sh` installs them for the snap, ADR 0085; the Flatpak can reuse both); the designed app icon is in `data/` (ADR 0074).
3. **A translation workflow for volunteers**, and **hardening**.
4. **Release** of 1.0.

Not scheduled:

- Sync.
